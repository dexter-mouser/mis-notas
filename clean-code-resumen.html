Capítulo 1

Código limpio

Clean Code

El desorden en el código no se nota el primer día, pero se acumula: cada cambio cuesta más que el anterior hasta que el equipo apenas avanza. Mantener el código limpio es parte del trabajo profesional, igual que un médico se lava las manos aunque tenga prisa.

  • El código limpio se lee como prosa bien escrita. Hace una sola cosa, la hace bien y no esconde sorpresas. Quien lo lee entiende qué pasa sin tener que adivinar.
  • Se lee diez veces más de lo que se escribe. Por eso conviene gastar tiempo en que sea fácil de leer: ese tiempo se recupera cada vez que alguien vuelve a él.
  • «Ya lo limpiaré luego» casi nunca ocurre. Las fechas de entrega siempre aprietan, y el desorden de hoy es lo que hará que la próxima entrega llegue tarde.
  • Regla del boy scout. Deja cada archivo un poco más limpio de como lo encontraste: un nombre mejor o una función partida. Muchas mejoras pequeñas evitan una reescritura grande.

Capítulo 2

Nombres con sentido

Meaningful Names

Los nombres están en todas partes: variables, funciones, clases y archivos. Un buen nombre responde por qué existe algo, qué hace y cómo se usa. Si necesitas un comentario para explicar un nombre, el nombre no sirve.

  • Revela la intención. diasDesdeCreacion se entiende sin contexto; d obliga a buscar dónde se asigna.
  • No desinformes. No llames listaClientes a algo que no es una lista ni uses nombres que solo se diferencian en una letra.
  • Haz distinciones con sentido. datos1 y datos2, o producto y productoInfo, no dicen en qué se diferencian.
  • Nombres pronunciables y fáciles de buscar. Si no puedes decirlo en voz alta en una reunión, ni encontrarlo con el buscador, cambia el nombre. Las constantes con nombre se encuentran; el número 7 suelto, no.
  • Sustantivos para clases, verbos para métodos. Cliente y Factura son cosas; guardar() y calcularTotal() son acciones.
  • Una palabra por concepto. Si en un sitio es obtener, no uses traer y conseguir en otros para lo mismo.

Antes

const d = 7;
function getThem(list) {
  const l1 = [];
  for (const x of list) if (x[0] === 4) l1.push(x);
  return l1;
}

Después

const diasDesdeCreacion = 7;
const ESTADO_MARCADA = 4;

function obtenerCeldasMarcadas(tablero) {
  return tablero.filter(celda => celda.estado === ESTADO_MARCADA);
}

Capítulo 3

Funciones

Functions

Las funciones son la primera unidad de organización del código. Una buena función es corta, hace una sola cosa y se lee de arriba abajo como una serie de pasos con nombre.

  • Pequeñas, y luego más pequeñas. Una función corta cabe en la cabeza de una vez. Si tiene secciones separadas por líneas en blanco, cada sección quiere ser una función.
  • Una sola cosa. Prueba práctica: si puedes extraer otra función con un nombre que no repita la descripción de la original, hacía más de una cosa.
  • Un nivel de abstracción por función. No mezcles «procesar el pedido» con «sumar 1 al índice». Los detalles bajan a funciones de nivel inferior.
  • Pocos argumentos. Cada argumento es algo más que entender y probar. Con más de tres, agrúpalos en un objeto con nombre.
  • Sin argumentos booleanos. Un true en la llamada no dice nada y revela que la función hace dos cosas. Sepárala en dos.
  • Sin efectos ocultos. Si comprobarClave() también inicia la sesión, alguien la llamará solo para comprobar y abrirá una sesión sin querer.
  • Separa órdenes de consultas. Una función cambia algo o responde algo, nunca las dos cosas a la vez.

Antes

function procesarPedido(pedido, enviarCorreo) {
  if (!pedido.items.length) return -1;
  let total = 0;
  for (const item of pedido.items) total += item.precio * item.cantidad;
  if (pedido.cupon) total *= 0.9;
  db.guardar({ ...pedido, total });
  if (enviarCorreo) correo.enviar(pedido.cliente, total);
  return 0;
}

Después

function procesarPedido(pedido) {
  validarQueTengaItems(pedido);
  const total = calcularTotal(pedido);
  guardarPedido(pedido, total);
}

function calcularTotal(pedido) {
  const subtotal = sumarItems(pedido.items);
  return aplicarCupon(subtotal, pedido.cupon);
}

// El correo lo envía quien llama, no un argumento booleano

Capítulo 4

Comentarios

Comments

Un comentario suele ser la señal de que el código no logró explicarse solo. Antes de escribirlo, intenta que el código diga lo mismo con nombres y funciones. Los comentarios no se ejecutan ni se prueban, así que se quedan desactualizados y terminan mintiendo.

  • Comentarios que sí valen. Avisos legales, la intención detrás de una decisión rara, advertencias («esta prueba tarda 10 minutos»), TODO con motivo y documentación de una API pública.
  • Comentarios que sobran. Los que repiten lo que el código ya dice, los obligatorios por norma en cada función y los que llevan un historial de cambios (para eso está el control de versiones).
  • Nunca dejes código comentado. Nadie se atreve a borrarlo porque «quizá importa», y se acumula. El control de versiones ya lo guarda.
  • Un comentario engañoso es peor que ninguno. El lector confía en él y deja de mirar el código.

Antes

// Comprueba si el empleado puede recibir todos los beneficios
if ((empleado.flags & FLAG_POR_HORA) && empleado.edad > 65) {
  // ...
}

Después

if (empleado.puedeRecibirTodosLosBeneficios()) {
  // ...
}

Capítulo 5

Formato

Formatting

El formato es comunicación: el orden, los espacios y la sangría le dicen al lector qué va junto y qué es importante. El código que funciona hoy cambiará mañana; el estilo y la legibilidad son lo que dura.

  • Como un artículo de periódico. El nombre del archivo es el titular, lo de arriba da la visión general y los detalles van hacia abajo.
  • Separación vertical entre conceptos. Una línea en blanco marca que empieza otra idea. Las líneas que van juntas, sin espacios entre ellas.
  • Cercanía según la relación. Declara las variables cerca de donde se usan y pon cada función justo debajo de la que la llama: así se lee hacia abajo sin saltar.
  • Líneas de ancho moderado. Si tienes que desplazarte a la derecha para leer, la línea hace demasiado.
  • Reglas del equipo, no personales. Un solo estilo para todo el proyecto, mejor si lo aplica un formateador automático.

Capítulo 6

Objetos y estructuras de datos

Objects and Data Structures

Hay dos formas de organizar datos. Los objetos esconden sus datos y ofrecen comportamiento. Las estructuras de datos muestran sus datos y no tienen comportamiento. Las dos sirven; el problema son los híbridos que hacen un poco de cada cosa.

  • Abstrae, no expongas. Poner un getter y un setter a cada campo no esconde nada. Ofrece operaciones con sentido: porcentajeDeCombustible() en vez de los litros y la capacidad del tanque por separado.
  • Cada forma tiene su ventaja. Con objetos es fácil agregar tipos nuevos sin tocar funciones existentes. Con estructuras es fácil agregar funciones nuevas sin tocar los datos. Elige según lo que más vaya a cambiar.
  • Ley de Demeter. Un método habla solo con sus vecinos directos. Las cadenas largas de llamadas atan tu código a la forma interna de otros objetos.
  • Objetos de transferencia. Para pasar datos entre capas (por ejemplo, la respuesta de una API) basta una estructura simple sin lógica.

Antes

const ciudad = pedido.getCliente().getDireccion().getCiudad();
calcularEnvio(ciudad);

Después

// El pedido sabe a dónde se envía; quien llama no recorre su interior
const costo = pedido.calcularCostoDeEnvio();

Capítulo 7

Manejo de errores

Error Handling

Las cosas fallan, y el código tiene que manejarlo. Pero si el manejo de errores se mezcla con todo, ya no se ve qué hace el programa. El objetivo es un código robusto que siga siendo legible.

  • Excepciones en vez de códigos de error. Un -1 obliga a quien llama a comprobarlo enseguida, y si se le olvida el error pasa desapercibido. Una excepción separa el camino normal del de error.
  • Empieza por el try-catch-finally. Define primero qué pasa si algo falla; el resto del código queda dentro de ese marco.
  • Da contexto. El mensaje debe decir qué operación falló y con qué dato, para depurar sin adivinar.
  • No devuelvas null. Cada null obliga a comprobarlo en todos los sitios, y basta olvidarlo una vez para que falle. Devuelve una lista vacía, un objeto de caso especial o lanza una excepción.
  • No pases null. Si una función no acepta null como dato válido, no se lo pases.

Antes

function buscarUsuario(id) {
  const fila = db.consultar(id);
  if (!fila) return null;
  return fila;
}

const usuario = buscarUsuario(5);
if (usuario !== null) {
  if (usuario.pedidos !== null) mostrar(usuario.pedidos);
}

Después

function buscarUsuario(id) {
  const fila = db.consultar(id);
  if (!fila) throw new UsuarioNoEncontrado(`No existe el usuario ${id}`);
  return fila;
}

function pedidosDe(usuario) {
  return usuario.pedidos ?? []; // lista vacía, nunca null
}

mostrar(pedidosDe(buscarUsuario(5)));

Capítulo 8

Límites

Boundaries

Casi todo proyecto usa librerías y servicios de otros. Su autor quiere servir a muchos casos; tú necesitas solo el tuyo. Si su API se usa en todo el proyecto, cada cambio de versión te obliga a tocar decenas de archivos.

  • Envuelve lo externo. Crea una interfaz propia y pequeña que exponga solo lo que usas. Si cambias de librería, cambias un archivo.
  • Pruebas de aprendizaje. Al conocer una API nueva, escribe pruebas que comprueben lo que esperas de ella. Te enseñan a usarla y, al actualizar la versión, te avisan si algo cambió.
  • Código que aún no existe. Si otro equipo no ha terminado su parte, define la interfaz que te gustaría tener, programa contra ella y adáptala cuando llegue la real.

Antes

// En veinte archivos distintos:
import axios from 'axios';
const respuesta = await axios.get(`/api/clientes/${id}`);
const cliente = respuesta.data;

Después

// clientesApi.js: único archivo que conoce la librería
import axios from 'axios';

export async function obtenerCliente(id) {
  const respuesta = await axios.get(`/api/clientes/${id}`);
  return respuesta.data;
}

// En el resto del proyecto:
const cliente = await obtenerCliente(id);

Capítulo 9

Pruebas unitarias

Unit Tests

Las pruebas permiten cambiar el código sin miedo. Si son desordenadas, cuesta tanto mantenerlas que se abandonan, y sin pruebas el código de producción vuelve a pudrirse. Merecen el mismo cuidado que el resto.

  • Las tres leyes de TDD. No escribas código de producción sin una prueba que falle; escribe solo la prueba justa para que falle; escribe solo el código justo para que pase. Así las pruebas cubren todo lo que haces.
  • La legibilidad manda. Una prueba es documentación ejecutable. Sigue la forma preparar, actuar y comprobar, y oculta los detalles repetitivos en funciones auxiliares.
  • Un concepto por prueba. Si falla, el nombre ya dice qué se rompió.
  • F.I.R.S.T. Rápidas (si tardan, no se ejecutan), independientes (ninguna depende de otra), repetibles (en cualquier máquina), con resultado claro (pasa o falla, sin revisar a mano) y escritas a tiempo (justo antes del código).

Antes

test('prueba1', () => {
  const c = new Carrito(); c.agregar({ p: 10, q: 2 }); c.agregar({ p: 5, q: 1 });
  expect(c.total()).toBe(25); c.vaciar(); expect(c.total()).toBe(0);
});

Después

test('el total suma precio por cantidad de cada producto', () => {
  // Preparar
  const carrito = new Carrito();
  carrito.agregar({ precio: 10, cantidad: 2 });
  carrito.agregar({ precio: 5, cantidad: 1 });
  // Actuar
  const total = carrito.total();
  // Comprobar
  expect(total).toBe(25);
});

test('un carrito vaciado tiene total cero', () => {
  const carrito = carritoConProductos();
  carrito.vaciar();
  expect(carrito.total()).toBe(0);
});

Capítulo 10

Clases

Classes

Las clases también deben ser pequeñas, pero se miden en responsabilidades, no en líneas. Un sistema con muchas clases pequeñas y bien nombradas es como un cajón con compartimentos etiquetados: encuentras lo que buscas sin revolver.

  • Responsabilidad única. Una clase debe tener un solo motivo para cambiar. Si para describirla dices «y», probablemente son dos clases.
  • Alta cohesión. Los métodos de una clase usan la mayoría de sus variables. Si un grupo de métodos usa solo una parte de las variables, ahí hay otra clase.
  • Organiza para el cambio. Agregar una función nueva debería significar agregar una clase, no editar una existente y arriesgarse a romperla (abierto a extensión, cerrado a modificación).
  • Depende de abstracciones. Si una clase usa una interfaz en lugar de una implementación concreta, puedes cambiar o simular esa pieza en las pruebas.

Antes

class Factura {
  calcularTotal() { /* ... */ }
  generarPdf() { /* ... */ }
  enviarPorCorreo() { /* ... */ }
  guardarEnBaseDeDatos() { /* ... */ }
}
// Cuatro motivos para cambiar: impuestos, diseño, correo y base de datos

Después

class Factura            { calcularTotal() { /* ... */ } }
class GeneradorPdfFactura { generar(factura) { /* ... */ } }
class NotificadorFacturas { enviar(factura, destino) { /* ... */ } }
class RepositorioFacturas { guardar(factura) { /* ... */ } }

Capítulo 11

Sistemas

Systems

Una ciudad funciona porque nadie la controla entera: hay equipos para el agua, la luz y el tráfico, cada uno con su nivel de detalle. Un sistema de software necesita la misma separación para crecer.

  • Separa construir de usar. Crear los objetos y conectarlos es una tarea distinta de usarlos. Hazla en un solo lugar (el arranque, main o una fábrica) y no la repartas por el código.
  • Inyección de dependencias. Una clase recibe lo que necesita en vez de crearlo. Así no queda atada a una base de datos o servicio concreto, y en las pruebas le pasas una versión falsa.
  • Separa lo transversal. Persistencia, seguridad, transacciones y registros afectan a todo, pero no deben mezclarse con la lógica de negocio.
  • Crece poco a poco. No hace falta diseñar todo el sistema por adelantado. Con las piezas bien separadas, la arquitectura puede crecer cuando la necesidad sea real.

Antes

class ServicioPedidos {
  constructor() {
    this.repositorio = new RepositorioMySql('prod-db:3306');
  }
}
// Imposible probarlo sin la base de datos real

Después

class ServicioPedidos {
  constructor(repositorio) {
    this.repositorio = repositorio;
  }
}

// main.js: el único lugar que construye el sistema
const servicio = new ServicioPedidos(new RepositorioMySql(config.db));

// En las pruebas
const servicioDePrueba = new ServicioPedidos(new RepositorioEnMemoria());

Capítulo 12

Emergencia

Emergence

Un buen diseño no tiene que planearse entero de antemano: aparece si sigues cuatro reglas simples, propuestas por Kent Beck, en este orden de importancia.

  • Pasa todas las pruebas. Un sistema que no se puede comprobar no se puede cambiar con confianza. Además, hacer el código fácil de probar empuja hacia clases pequeñas y poco acopladas.
  • No tiene duplicación. Cada duplicado es trabajo extra y un riesgo: si cambias una copia y olvidas la otra, aparece un error. Eliminarla suele revelar abstracciones útiles.
  • Expresa la intención. Nombres claros, funciones y clases pequeñas, y pruebas que sirvan de ejemplo. La mayor parte del costo de un proyecto está en mantenerlo.
  • Minimiza clases y métodos. No crees una interfaz para cada clase ni separes por dogma. Esta regla es la menos importante: las tres anteriores van primero.

Capítulo 13

Concurrencia

Concurrency

La concurrencia separa qué se hace de cuándo se hace, y eso puede mejorar el rendimiento. Pero introduce errores que aparecen solo a veces, son difíciles de reproducir y no se ven al leer el código.

  • Mitos. La concurrencia no siempre mejora el rendimiento, sí cambia el diseño y no basta con entender el lenguaje: hay que entender los problemas clásicos.
  • Aísla el código concurrente. Tiene su propio ciclo de cambios y sus propias dificultades. Mantenlo separado del resto.
  • Limita los datos compartidos. Cuantos menos datos compartan los hilos, menos sitios donde pueden pisarse. Prefiere copias y datos independientes.
  • Conoce los modelos clásicos. Productor-consumidor, lectores-escritores y la cena de los filósofos explican la mayoría de los problemas reales.
  • Secciones sincronizadas pequeñas. Los bloqueos cuestan rendimiento; protege solo lo imprescindible.
  • Prueba en serio. Ejecuta las pruebas muchas veces y en distintas configuraciones. Un fallo esporádico no es mala suerte: es un error real.

Antes

// Dos peticiones a la vez leen el mismo saldo y una pisa a la otra
const saldo = await db.leerSaldo(cuenta);
await db.guardarSaldo(cuenta, saldo - monto);

Después

// La base de datos resta en una sola operación atómica
await db.ejecutar(
  'UPDATE cuentas SET saldo = saldo - ? WHERE id = ?',
  [monto, cuenta]
);

Capítulo 14

Refinamiento sucesivo

Successive Refinement

Caso práctico: un analizador de argumentos de línea de comandos. El autor muestra primero una versión que funciona pero está enredada, y después la limpia paso a paso.

  • El primer borrador nunca sale limpio. Escribir código es como escribir un texto: primero lo haces funcionar y luego lo pules. No hacerlo es abandonar el trabajo a medias.
  • Para antes de que se pudra. El autor vio que cada tipo de argumento nuevo complicaba el código, y paró a reorganizar antes de agregar más.
  • Cambios pequeños y pruebas siempre. Cada paso deja el programa funcionando. Así un error nunca está lejos del último cambio.
  • El desorden crece en silencio. Limpiar algo de hace cinco minutos es fácil; limpiar algo de hace meses, con todo construido encima, es carísimo.

Capítulo 15

Aspectos internos de JUnit

JUnit Internals

Caso práctico: el autor revisa un módulo de JUnit que ya estaba bien escrito y aun así encuentra mejoras.

  • Hasta el buen código puede mejorar. Quita prefijos innecesarios de los nombres, encapsula condiciones en funciones con nombre y parte las funciones largas.
  • Pequeñas mejoras se suman. Ningún cambio es grande, pero juntos hacen el módulo más fácil de leer.
  • Es la regla del boy scout aplicada a código ajeno. Mejorar lo que no escribiste también es tu responsabilidad.

Capítulo 16

Refactorizar SerialDate

Refactoring SerialDate

Caso práctico: revisar y refactorizar una clase de fechas de una librería de código abierto real, con respeto por el trabajo de su autor.

  • Primero, las pruebas. Antes de tocar nada, el autor amplía la cobertura de pruebas, y al hacerlo descubre errores que ya existían.
  • Después, limpiar. Quita dependencias innecesarias, código muerto y nombres confusos, y mueve cada método a la clase donde tiene sentido.
  • Criticar con respeto es parte del oficio. Señalar problemas en el código de otro, con argumentos, es como se mejora en equipo.

Capítulo 17

Olores y heurísticas

Smells and Heuristics

Catálogo de señales de que el código necesita limpieza, reunido a lo largo del libro. Cada señal tiene un código (C1, F1, G1…) para nombrarla en las revisiones.

  • Comentarios. Obsoletos, redundantes, mal escritos o con código comentado.
  • Entorno. Compilar o ejecutar las pruebas requiere más de un paso.
  • Funciones. Demasiados argumentos, argumentos de salida, argumentos booleanos y funciones que nadie llama.
  • Generales. Duplicación, niveles de abstracción mezclados, números mágicos, condiciones sin encapsular, comportamiento obvio que falta y código en la clase equivocada.
  • Nombres. Poco descriptivos, que no reflejan su nivel de abstracción o que esconden efectos secundarios.
  • Pruebas. Insuficientes, lentas, que ignoran los casos límite o que se desactivan sin explicación.

Antes

if (usuario.intentos > 3 && Date.now() - usuario.ultimoIntento < 900000) {
  bloquear(usuario);
}

Después

const MAX_INTENTOS = 3;
const VENTANA_BLOQUEO_MS = 15 * 60 * 1000;

function superoIntentosRecientes(usuario) {
  const esReciente = Date.now() - usuario.ultimoIntento < VENTANA_BLOQUEO_MS;
  return usuario.intentos > MAX_INTENTOS && esReciente;
}

if (superoIntentosRecientes(usuario)) bloquear(usuario);

Concurrencia II

Concurrency II

Amplía el capítulo 13 con un ejemplo de cliente-servidor y un análisis de los bloqueos.

  • Lo que parece atómico no lo es. Una operación de una sola línea, como incrementar un contador, son varios pasos para la máquina, y otro hilo puede colarse entre ellos.
  • Las cuatro condiciones del interbloqueo. Exclusión mutua, retener mientras se espera, sin expropiación y espera circular. Si rompes cualquiera de ellas, el interbloqueo no puede ocurrir.
  • Mide antes de concurrir. En el ejemplo de cliente-servidor, primero se averigua dónde se pierde el tiempo y luego se decide qué paralelizar.
  • Prueba el código multihilo. Fuerza intercalados distintos con pausas o herramientas específicas, para que los fallos raros aparezcan antes de producción.
